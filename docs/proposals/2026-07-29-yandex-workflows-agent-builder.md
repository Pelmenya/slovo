# Агент-конструктор Workflows: разбор и тема для обсуждения

> Написано после вебинара AI Studio Series «Как создавать мультиагентные системы для end-to-end автоматизации процессов» (29 июля 2026).
>
> **Что это.** Не предложение и не заявка — наблюдение и гипотеза, которые хочется обсудить. Первая часть — фактура, она проверяема: всё о платформе взято из публичной документации и официального репозитория, ссылки в конце. Дальше — выводы, и вот они уже спорные, поэтому и выносятся на обсуждение.
>
> **Кто пишет.** Практикующий разработчик в постоянной паре с агентом (Claude Code). Не команда и не вендор: два участника, один из которых языковая модель. Это существенно для содержания — почему, объясняется в разделе 4.

## Если коротко

Спецификация workflow — обычный текст YAML. REST API умеет `Create` и `Update`. Официальный `workflows-mcp-server` даёт агенту и создание workflow, и чтение истории исполнений.

Из этого следует, что петля «сгенерировал → запустил → прочитал результат → исправил» замыкается **уже сегодня**, без единой строчки нового кода со стороны платформы.

Наблюдение: пользуется этой петлёй разработчик у себя в IDE. Бизнес-пользователь, ради которого идёт весь low-code трек, до неё не дотягивается — хотя это как раз он не знает, из каких кубиков сложить свой процесс.

Гипотеза: тот же цикл мог бы жить внутри конструктора. Описал задачу словами — получил черновик на холсте; дальше либо правишь кубики руками, либо продолжаешь уточнять словами, и агент дорабатывает сам.

Насколько это осмысленно и не противоречит ли планам команды — собственно, предмет обсуждения.

## 1. Что в платформе уже есть

Это фактическая часть, здесь спорить не о чем — можно только поправить, если я что-то прочитал неверно.

### 1.1. Спецификация — текст, а не картинка

YaWL версии `0.1`. Обязательные элементы: `yawl`, `start`, `steps`; опционально `defaultRetryPolicy`.

**Интеграционные шаги:** HTTPCall, gRPCCall, Cloud Functions, Serverless Containers, YDB, Object Storage, Message Queue, Data Streams, Foundation Models, OCR, Speech-to-Text, Tracker, Postbox, Telegram, Vector Store.

**Управляющие шаги:** Switch, Foreach, While, Parallel, Success, Fail, NoOp, Wait.

**Общие поля интеграционного шага:** `input`/`output` (фильтрация через jq), `next`, `retryPolicy`, `timeout` (по умолчанию 15 минут), `catch`.

### 1.2. REST API покрывает жизненный цикл

Ресурс `Workflow`: `Create`, `Update`, `Get`, `Delete`, `List`. Плюс ресурсы `Execution` и `Operation`.

В теле `Create` — поле `specification` типа `WorkflowSpecification`, внутри единственное поле **`specYaml` (string)**: спецификация как строка YAML. Рядом — `folderId`, `name`, `description`, `labels`, `serviceAccountId`, `logOptions`, `networkId`, `express`, `schedule`, `isPublic`.

Отсюда следует вещь, на которой держится всё дальнейшее: **чтобы создать workflow программно, достаточно сгенерировать корректный текст.** Промежуточного графического представления не существует.

### 1.3. MCP-сервер управления уже написан и официален

В репозитории `yandex-cloud/mcp` есть отдельный **Workflows MCP Server** — «создание и управление serverless workflows с YAML-спецификациями, выполнениями и планированием». Среди его инструментов:

| Группа              | Инструменты                                                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Управление ресурсом | `workflow_create`, `workflow_update`, `workflow_get`, `workflow_delete`, `workflows_list`                                                  |
| Исполнения          | `workflow_execution_start`, `workflow_execution_stop`, `workflow_execution_terminate`, `workflow_execution_get`, `workflow_execution_list` |
| Обратная связь      | **`workflow_execution_history_get`**                                                                                                       |
| Служебное           | `workflow_operations_list`, `workflow_accesses_list`, `workflow_accesses_update`                                                           |

Соседние серверы того же репозитория закрывают Functions, Serverless Containers, Triggers, API Gateway, MCP Gateway, документацию и поиск.

**И вот главное наблюдение по фактам.** Связка

```
workflow_create → workflow_execution_start → workflow_execution_history_get → workflow_update → ↺
```

— это законченная петля самопроверки. Агент может сгенерировать флоу, запустить, прочитать что реально произошло на каждом шаге, найти расхождение и исправить спецификацию. Всё — существующими инструментами, ничего дописывать не нужно.

### 1.4. Дополнительная обратная связь в интерфейсе

- **Режим отладки** — пауза на конкретном шаге, подстановка произвольного `input`, пошаговое исполнение и `continue`, просмотр `output` шага без прогона всего префикса.
- **История исполнений** — видно, что реально пришло на вход и что вернул каждый шаг.

### 1.5. MCP Hub замыкает контур со стороны агента

Workflow оборачивается в MCP-инструмент (роль `workflows.executor` на сервисном аккаунте) и подключается к агенту в Agent Atelier. MCP-серверы бывают приватные и публичные; в MCP Hub можно собрать сервер с нуля из инструментов вида HTTPS-запрос, Cloud Functions или Workflows.

### 1.6. Suggest

UI-генератор jq-выражений для передачи контекста между шагами. Под капотом тот же jq — технический пользователь может написать выражение руками.

## 2. Наблюдение: где, как мне кажется, разрыв

Дальше начинается интерпретация, и с ней уже можно спорить.

### 2.1. Инструмент есть, но, похоже, не для той аудитории

На вебинаре прозвучало прямо: сервис изначально делался для DevOps и разработчиков, а сейчас идёт трек на low-code, «чтобы в нём могли работать бизнес-пользователи».

Но `workflows-mcp-server` — инструмент ровно старой аудитории. Он живёт в конфиге IDE, ставится руками, требует IAM-токена и понимания, что такое MCP. Отличный «VibeDevOps» для разработчика — и, кажется, недосягаемая вещь для менеджера, который пришёл автоматизировать согласование заявок.

Получается вилка, и мне она видится так: **самая мощная возможность досталась тем, кому она нужна меньше всего.** Разработчик и так соберёт флоу руками. Не соберёт как раз бизнес-пользователь — и именно он до MCP не дойдёт.

### 2.2. Две оси упрощения, занята одна

|                 | Ось A — упростить сборку                   | Ось B — убрать сборку                                  |
| --------------- | ------------------------------------------ | ------------------------------------------------------ |
| Что делает      | пользователь собирает флоу сам, но проще   | пользователь описывает задачу, флоу собирается за него |
| В продукте      | Suggest, low-code UI, готовые кубики       | нет                                                    |
| Стартовая точка | пустой холст                               | текст задачи                                           |
| Кому помогает   | тому, кто уже знает, какой у него pipeline | тому, кто знает только желаемый результат              |

Suggest снимает вопрос «как достать поле из предыдущего шага». Он не снимает вопрос **«из каких шагов вообще должен состоять мой процесс»** — а для бизнес-пользователя, по моему опыту, это и есть главный барьер. Он приходит с формулировкой «хочу, чтобы заявки из формы сами проверялись и уходили на согласование», а не со схемой из семи кубиков.

### 2.3. Петля есть, но её никто не замкнул как продукт

Все части существуют по отдельности. Не видно места, где они собраны в цикл, который доводит флоу до рабочего состояния сам. Сегодня это ручная работа разработчика, вооружённого MCP-сервером.

### 2.4. Направление «агент строит workflow» нигде не заявлено

На вебинаре финальный блок назывался «Workflows как MCP-tool для агента» — агент _вызывает_ готовый workflow, и аргумент был точный: детали процесса не протекают в его контекст. Обратное направление — агент _строит_ workflow — не прозвучало ни разу, хотя `workflow_create` лежит в официальном MCP-сервере уже сейчас.

Это разрыв не в коде, а в позиционировании: возможность есть, но не оформлена как обещание пользователю. Возможно, сознательно — и это как раз то, что интересно узнать.

## 3. Как это могло бы выглядеть

Слой управления писать не нужно, он уже есть. Гипотеза начинается там, где он заканчивается.

### Путь от задачи к спецификации

Не «сгенерируй YAML по промпту» — этого мало и это ненадёжно. Скорее промежуточные артефакты, каждый из которых человек может прочитать и поправить:

```
описание задачи словами
  → требования: что на входе, что на выходе, чего делать нельзя
  → фазы и контрольные точки
  → черновик YaWL: шаги, ветвления, точки интеграции
  → workflow_create
```

Смысл промежуточных шагов — ошибку видно на дешёвом уровне. Неверно понятое требование ловится в тексте требований, а не в отладке YAML на 200 строк.

### Петля самовалидации как часть продукта

Строить почти нечего: все четыре инструмента уже есть. Задача — оформить цикл, критерий остановки и предъявление результата человеку. Без цикла получается демо, которое впечатляет одну минуту; с ним — инструмент, доводящий флоу до рабочего состояния.

### Это должно жить в интерфейсе, а не в терминале

Самая важная часть и единственная, которую нельзя закрыть внешними силами.

В конструкторе появляется вход «опишите задачу словами». Дальше та же петля, но без установки MCP, без IAM-токена, без терминала. Результат — **заполненный черновик на холсте**, а не чёрный ящик.

Агент не заменяет UI, он убирает пустой холст. Дальше человек правит кубики руками, всеми привычными инструментами, включая suggest. Low-code трек это не отменяет, а скорее усиливает: суть low-code в том, чтобы снизить порог входа, а нет порога ниже, чем описать задачу словами.

### Править тоже словами, а не только руками

Здесь уточнение, которое меняет масштаб всей идеи: править полученный черновик пользователь мог бы разговором, а не только мышкой.

> «Добавь ветку на случай, если сумма заявки больше 100 тысяч» → агент меняет спецификацию → флоу на холсте обновляется.

Технически это не новая функциональность. Это тот же `workflow_update` из существующего MCP-сервера, просто вызванный не разработчиком из терминала, а пользователем из интерфейса обычной фразой.

Два следствия, каждое существеннее, чем кажется сначала.

**Диалог сильнее ручной правки, а не слабее.** Человек, правящий кубик руками, видит только сам кубик. Агент в этот момент видит ещё и историю исполнений — что реально пришло на вход и что вернулось на каждом шаге. То есть правит не вслепую, а по факту прогона. Это качественно другая позиция, и пользователю, кликающему по холсту, она недоступна.

**Снимается ограничение на размер флоу.** Не нужно генерировать весь процесс одним выстрелом и надеяться, что модель не ошибётся на двадцатом шаге. Флоу растёт инкрементально: фраза — изменение — прогон — следующая фраза. Каждый шаг проверяем, каждый обратим. Именно так работает наша пара человек-агент в повседневной разработке, и именно поэтому получается объём, описанный в разделе 4.

Холст при этом остаётся источником правды. Пользователь в любой момент переключается на ручную правку и обратно — кому-то удобнее сказать, кому-то показать. Ценность в том, что **выбор появляется**: сегодня единственный способ изменить флоу — собрать его руками.

## 4. Почему мне кажется, что это реалистично

Мы прошли похожий путь на Flowise — визуальном конструкторе LLM-пайплайнов, близком по духу. Не как эксперимент, а как рабочая инфраструктура.

Сразу уточню, кто такие «мы», потому что это не фигура речи. **Нас двое: один разработчик и агент, работающие в постоянной паре.** Всё перечисленное ниже построено этой парой — не отделом, не подрядчиком.

Это делает раздел не только рассказом об опыте, но и косвенным аргументом по существу. Тезис в том, что агент способен собирать рабочие пайплайны в визуальном конструкторе. Аргумент в его пользу — то, что MCP-сервер на 66 инструментов, типизированный конструктор графа и продуктовые фичи поверх них написаны ровно таким способом. Будь тезис неверен, этого объёма при таком размере команды не получилось бы.

**Что построено:**

- **MCP-сервер на 66 инструментов** — полное зеркало REST API Flowise: хранилища документов (22 инструмента, включая чанки, загрузчики и векторное хранилище), флоу, интроспекция каталога узлов, запуск предсказаний, учётные данные, переменные, кастомные инструменты, ассистенты, составные помощники. Функционально это прямой аналог вашего `workflows-mcp-server` — просто написанный нами, потому что готового не было.
- **Типизированный конструктор графа флоу** — 12 фабрик для частых узлов плюс универсальный fallback через runtime-интроспекцию каталога. Агент собирает флоу не из памяти модели, а из машинного каталога того, что реально есть в системе.
- Поверх этого — работающие продуктовые фичи: поиск по товарному каталогу по тексту и фотографиям и пайплайн анализа воды (15 504 документа лабораторных бланков, приведённых к структурированному датасету с векторным поиском и набором API).

**Главный вывод из этого опыта, и он прямо про обсуждаемую ситуацию:**

> Наличие MCP-сервера над конструктором закрывает примерно треть задачи. Он даёт агенту руки, но не даёт ни понимания, что строить, ни способа убедиться, что построенное работает.

Мы выяснили это на себе: сервер на 66 инструментов был готов задолго до того, как из него начал получаться предсказуемый результат. Работать начало, когда добавились две вещи — генерация строго из машинного каталога узлов и обязательная проверка результата после каждого создания.

**И честная часть — почему на YaWL, по-моему, будет заметно легче, чем было нам.**

Во Flowise флоу — это `flowData`: JSON с координатами узлов, идентификаторами точек соединения и путями к иконкам. Мы регулярно ловили класс дефектов, когда REST возвращал структурно валидный JSON, флоу исполнялся, но **интерфейс не рисовал связи** — из-за рассогласования handles с якорями узла. Пришлось добавить отдельную проверку скриншотом браузера после каждого создания, потому что ответ API не гарантировал корректной картинки.

|                         | Flowise flowData       | YaWL                        |
| ----------------------- | ---------------------- | --------------------------- |
| Представление           | граф с геометрией      | плоская декларативная спека |
| Связи                   | source/target handles  | поле `next`                 |
| Передача данных         | привязка к точкам узла | jq в `input`/`output`       |
| Валидация до применения | практически невозможна | разбор YAML + схема         |
| Расхождение API и UI    | реальный класс багов   | не возникает                |

Самая дорогая часть нашего опыта здесь просто не нужна. Текстовая декларативная спецификация — ровно тот формат, который языковая модель генерирует надёжнее всего и который детерминированно проверяется **до** обращения к API.

## 5. Как это дёшево проверить

Гипотеза проверяемая, и проверка стоит недорого. Сценарий удобно взять из самого вебинара — тот, что показывали как пример кастомной интеграции:

> Яндекс.Форма → webhook → Cloud Function (ffmpeg: из видео оставить аудио, положить в Object Storage) → Speech-to-Text → агент со строгой JSON-схемой (`title`, `description`, `description` в HTML) → Postbox + запись в Object Storage.

Вход — текстовое описание этого процесса словами. Выход — созданный через `workflow_create` и успешно отработавший workflow.

**Метрика одна: сколько итераций петли нужно до зелёного прогона.** Две-три — гипотеза жива. Существенно больше — честный отрицательный результат, и это тоже полезный ответ, просто другой.

Объём — порядка одного вечера при наличии доступа к API. Сам этот сценарий у нас уже собран локально в другой реализации, так что сравнивать результат есть с чем.

## 6. Что может пойти не так

Здесь без смягчения, потому что это самая полезная часть для обсуждения.

- **Длинные флоу.** Качество генерации падает с ростом числа шагов — если пытаться выдать весь процесс одним выстрелом. Лечится инкрементальным ростом через диалоговую правку: агент собирает скелет, дальше флоу достраивается по фразе за раз, и каждое изменение проверяется прогоном. Требование «сгенерировать двадцать шагов безошибочно с первой попытки» при таком режиме не возникает.
- **Выдуманные имена шагов и полей.** Модель может изобрести несуществующий кубик. Единственное рабочее лечение, которое мы нашли, — генерировать строго из машинного каталога доступных шагов, а не из памяти модели. В документации `workflows-mcp-server` валидация спецификации не описана, так что это, возможно, ближайший пробел.
- **Права и аудит.** Агент, создающий workflow, — это уже не `workflows.executor`, а роль на изменение. Нужен отдельный аудит-след: кто и по какому запросу создал ресурс. В интерфейсном варианте это становится обязательным, а не опциональным.
- **Это не про голосовых агентов.** На вебинаре прозвучал точный ответ: Workflows — про длинные циклы обработки, для realtime-сценариев голосового агента не подходит. Ничего из написанного выше с этим не спорит и этой области не касается.
- **Черновик остаётся черновиком.** Ответственность за продуктивный запуск — на человеке, который его прочитал и принял. Такой инструмент экономит первые 80% пути, но не отменяет ревью.

## 7. Открытые вопросы

Собственно, то, ради чего это написано.

**К команде:**

1. **Есть ли направление «агент строит и правит workflow» в планах?** Если да — дальше обсуждать нечего, и это лучший исход: значит, оно появится. Если нет — интересно узнать, это осознанное решение или просто руки не дошли.
2. **Планируется ли валидация спецификации без создания ресурса** — dry-run для `workflow_create`? Это резко удешевляет любую петлю: ошибку видно до обращения к API, а не после неудачного прогона.
3. **Существует ли машиночитаемый каталог шагов** — перечень типов с их полями — и публичная JSON-схема YaWL? Из всего перечисленного это самая дешёвая вещь с наибольшим эффектом: она напрямую снимает риск выдуманных имён и поднимает долю флоу, валидных с первой попытки.

**К сообществу:**

4. **Пробовал ли кто-то генерировать YaWL агентом, и что получалось?** Интересен любой опыт, включая отрицательный: где ломалось, на каком размере флоу, что помогало.
5. **Насколько описанный барьер вообще реален?** Возможно, я переоцениваю проблему пустого холста, и на практике бизнес-пользователи спокойно собирают флоу руками, а мешает им что-то совсем другое.
