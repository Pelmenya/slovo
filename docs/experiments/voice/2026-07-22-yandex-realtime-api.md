# Yandex AI Studio Real-Time API — разбор и следствия для apps/voice

> **Дата:** 2026-07-22
> **Источник:** вебинар «Yandex AI Studio Series Summer Edition 2026 — Real-Time API: голосовые приложения от простых до мультиагентских» (команда AI Studio).
> **Метод:** видео 1:43:35 прогнано через `video-transcriber` (Groq Whisper), транскрипт разобран целиком.
> **Статус:** research-находка. Решение не принято — кандидат в ADR.

---

## Зачем разбирали

`apps/voice` строит голосового робота для клиник: исходящий звонок-напоминание, подтверждение/перенос/отмена, запись статуса обратно в МИС. Собственный контур: Asterisk/ARI (телефония), SpeechKit (TTS/STT), рукописная state machine + классификатор (диалог).

Вопрос: что из этого уже закрыто платформой, а что остаётся нашей работой.

---

## Что Yandex Real-Time API даёт из коробки

| Слой               | Что даёт                                                                                                                                                                      |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Голосовой рантайм  | Каскад ASR → LLM → TTS по WebSocket. **Совместимость с протоколом OpenAI Real-Time** — работает готовый OpenAI Agents SDK (Python/TypeScript)                                 |
| Конструктор        | Playground без кода: промпт, голос и амплуа, параметры речи (длительность тишины 850 мс, чувствительность), тест в браузере                                                   |
| Инструменты        | function calling, **MCP Hub**, file search (индекс документов, свой чанкинг через JSONL), web search                                                                          |
| Переменные промпта | Параметризация до звонка: имя пациента, время записи, **свободные слоты для переноса** — без похода в CRM во время разговора                                                  |
| Truncate           | Обработка перебиваний: модель знает, какую часть реплики абонент реально дослушал                                                                                             |
| Мультиагентность   | Паттерн «диспетчер + handoff», разные голоса и наборы инструментов на агента                                                                                                  |
| Телефония          | Три пути: (1) свой медиашлюз WebSocket ↔ SIP/RTP, (2) партнёры (VoxImplant), (3) **экспериментальный SIP-endpoint Яндекса** — направляешь свой транк к ним, агент собран в UI |

Заявленные планы (осень 2026): живее голоса под операторские сценарии, умнее realtime-модели, больше функций и контекста, observability.

**Клиника — их собственный пример** в презентации: «звоните в клинику, хотите записаться к врачу по фамилии», и отдельно — сценарий напоминания с предзаполненными слотами для переноса. То есть наш кейс платформа считает целевым.

## Что это означает для нашего стека

Слои, в которые мы вложились, платформа закрывает коробкой:

| Наш компонент                                       | Статус                                                               |
| --------------------------------------------------- | -------------------------------------------------------------------- |
| `libs/voice/telephony` (Asterisk/ARI)               | Закрывается SIP-endpoint'ом или партнёрской телефонией               |
| `libs/voice/speech` (SpeechKit TTS/STT)             | Внутри рантайма, отдельная обвязка не нужна                          |
| `libs/voice/dialog` (state machine + классификатор) | Заменяется промптом + function calling; перебивания — через truncate |

Важно: **мы уже внутри экосистемы** — SpeechKit и AI Studio используются в `libs/voice` сегодня, юрисдикция РФ под 152-ФЗ соблюдается. Переход на Real-Time API — консолидация у того же вендора, а не новая зависимость и не новый комплаенс-риск.

**Вывод: дальнейшие вложения в speech/telephony/dialog-слои нецелесообразны.**

---

## Где остаётся наша ценность

1. **MCP-сервер под МИС клиники** — платформа даёт механизм (MCP Hub), но интеграцию под конкретную МИС пишет исполнитель. Контракт вертикали: `find_patient`, `get_appointments`, `list_free_slots`, `create_appointment`, `patch_confirmation`, `get_prices`. Это и есть продукт.
2. **Бизнес-аналитика и промпт как услуга** — авторы прямо отметили, что написание рабочего промпта требует «ненулевой работы, подчас бизнес-аналитики», и сравнили это с ремонтом, где зовут специалистов.
3. **Мультитенантность и эксплуатация** — платформа про одного агента, не про парк клиник: конфиг на тенанта, мониторинг, SLA. Модель `Clinic` остаётся актуальной.
4. **Observability** — признанный пробел платформы на текущий момент.

Совпадение компетенции: `apps/mcp-flowise` (66 typed tools, зеркало Flowise REST) — это ровно навык подключения через MCP, то есть точка интеграции их платформы.

---

## Окна возможностей

- **Экспериментальный SIP-endpoint** — ограничен по числу участников, планируется общий доступ. Ранний вход имеет смысл.
- **AI Studio Scale (сентябрь 2026) + челлендж**: заявленные гранты и помощь в реализации для отобранных идей. Робот записи для клиник соответствует профилю кейсов.

---

## Что НЕ делаем

- Не дорабатываем `libs/voice` в частях telephony / speech / dialog-state-machine.
- Не пишем собственный медиашлюз WebSocket ↔ SIP, пока доступны SIP-endpoint и партнёрская телефония.
- Не переписываем уже работающее: перенос на новый рантайм — отдельное решение (ADR), а не рефакторинг «по ходу».

---

## Открытые вопросы

1. Тарификация Real-Time API за минуту разговора против собственного контура на объёме парка клиник.
2. Доступность экспериментального SIP-endpoint для нашего транка (Novofon) — нужен запрос.
3. Глубина контроля над диалогом: хватает ли промпта и function calling там, где сейчас детерминированная state machine (юридически значимые подтверждения).
4. Observability и хранение стенограмм звонков под 152-ФЗ при обработке на стороне платформы.
5. Судьба модели `Clinic` и таблиц `Call` / `CallTurn` — остаются как слой парка и аудита.
